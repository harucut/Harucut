# 아키텍처 결정 기록

> **아키텍처 결정만** 남긴다. 기준은 "되돌리는 비용"이다.
>
> | 남긴다 | 남기지 않는다 |
> |--------|---------------|
> | 대안 기술이 있었던 선택 | 코드 레벨 선택 (record vs class, 네이밍, 반환 타입) |
> | 되돌리려면 여러 도메인·파일이 바뀌는 것 | 한 파일만 고치면 되돌아가는 것 |

>
> **"포기한 것"을 못 쓰겠으면 트레이드오프를 아직 이해 못 한 것이다.** 다시 생각한다.
>
> **정렬은 오래된 것이 위(작성 순)다.** 새 결정은 «기록 후보» 앞에 덧붙인다.
> 항목 형식은 `- **라벨**: 내용` 한 줄로 통일하고, 후보 목록만 중첩 불릿으로 둔다.
> 여러 머신에서 편집하면 이 규칙을 먼저 확인할 것 — 한 번 이어붙임 사고가 났다.

## 2026-08-14 — 인가 정보(role/status)를 access 토큰 클레임으로 옮김 (`8be3706`)

> 과정과 근거 전체는 [`jwt-authorization-claims.md`](jwt-authorization-claims.md).

- **배경**: `JwtAuthenticationFilter`가 매 요청 DB를 읽었다. 토큰에 `sub`와 `type`뿐이라 authorities를 계산할 재료가 없어서다. 문제는 조회 1회의 비용이 아니라, **캐시로 끝날 수 있는 요청까지 DB 커넥션을 잡는다**는 것이다.
- **후보**:
  - 그대로 두기 — 취소가 즉시 반영되는 현 상태 유지
  - role/status를 access 토큰 클레임으로 (선택)
  - role/status/id를 전부 클레임으로 — 쓰기 API까지 조회 0
  - principal을 Redis에 캐싱하고 차단 시 무효화 — DB를 Redis로 바꾸는 것이지 없애는 건 아님
  - `spring-security-oauth2-resource-server`로 전환
- **선택**: `role`, `status`만 access 토큰의 private claim으로 넣고 필터의 DB 조회를 제거한다. **`id`는 넣지 않는다.** refresh 토큰에는 넣지 않는다. principal 타입을 둘로 쪼갠다 — `CustomUserPrincipal`(로그인 심사용 `UserDetails`, DB에서 생성)과 `AuthenticatedUser`(요청 컨텍스트용 `AuthenticatedPrincipal`, 토큰에서 생성).
- **이유**: 인가는 `authorizeHttpRequests`·`@PreAuthorize` 시점에 끝나야 하므로, role/status를 토큰에서 얻지 못하면 조회를 뺄 방법이 없다. `id`를 빼는 건 실제 필요가 Phase 8에서 드러나기 때문이고, 지금 넣으면 근거 없이 내부 PK만 노출한다. refresh에 넣지 않는 건 회전 때 옛 값이 복사되어 14일간 갱신이 멈추기 때문이다. 타입 분리는 토큰으로 만든 principal의 `id`/`email`/`password`가 null일 수밖에 없어서다 — 한 클래스로 두면 `getId()`가 조용히 null을 돌려주고, 나눠두면 컴파일이 막는다. 리소스 서버 전환은 발급·회전이 어차피 우리 몫이라 얻는 게 검증 쪽 절반뿐이고, 에러 봉투를 맞추려면 결국 커스텀이 필요해 실속이 준다.
- **포기한 것**:
  - **취소가 최대 30분(access TTL) 늦게 반영된다.** 상한이 성립하는 근거는 세션 삭제가 아니라 **재발급이 DB를 다시 읽는 것**이다. 차단 → 재발급 시 `BLOCKED`가 새 토큰에 실림 → authorities 는 `ROLE_BLOCKED` 하나 → 마이페이지·탈퇴 말고 403 `AUTH-042`.
  - 재발급 경로에 DB 조회가 **새로 생긴다.** 조회가 사라진 게 아니라 매 요청에서 30분마다로 옮겨간 것이다.
  - **필터에서 없앤 것이지 요청 전체가 DB-free가 된 것은 아니다.** `user_id` FK가 필요한 쓰기 API는 서비스에서 `publicId`로 다시 조회하므로 조회 횟수가 그대로다(`PaymentService`·`CouponService`·`ComposeService`·`SubscriptionService` 모두 `findByPublicId`). 요청 전체가 조회 0이 되는 건 `/auth/status`·`logout`처럼 서비스가 User를 필요로 하지 않는 경로뿐이다. 그 API들은 즉시성만 잃는다.
  - 배포 시점에 살아 있던 access 토큰이 전부 무효가 된다(클레임 누락 → 거부). 서비스 전이라 감수한다.
  - 인가 판정 재료가 서명된 토큰 안으로 들어가므로, **키가 유출되면 권한까지 위조된다.** 전에는 DB가 최종 권위였다.
- **다시 볼 시점**: `id` 클레임은 **결론이 났다** — Phase 8 이후 쓰기 API가 전부 구현됐는데 `getReference(User.class, id)`를 쓰는 곳이 한 군데도 없고, 서비스가 `publicId`로 User를 읽어 FK를 세팅하는 방식으로 정착했다. 넣지 않는다. (2026-11 A17: 정지 API·세션 삭제·관리 경로 재확인이 들어왔다 — `jwt-authorization-claims.md` 4절. 아래는 그 전의 기록이다) 30분이 길다고 판단되면 access TTL을 줄이기 전에 차단 시 refresh 세션 삭제를 먼저 넣는다(TTL을 줄이면 재발급 트래픽이 Redis+Lua를 탄다) — **다만 지금은 `BLOCKED`로 전환하는 코드 자체가 없어서**(`User`의 상태 대입은 ACTIVE·DELETED_REQUESTED·DELETED뿐) 이 30분 대가를 실제로 치를 일이 아직 없다. 소셜 로그인이 진짜 OAuth2 흐름을 타거나 외부 클라이언트에 토큰을 발급하게 되면 리소스 서버 전환을 다시 올린다.

## 2026-08-14 — refresh 토큰 회전에 grace 윈도우 도입

- **배경**: 회전 + 재사용 감지가 정상적인 동시 요청을 공격으로 오인했다. 앱이 401을 받고 refresh를 두 번 던지면(탭 두 개, 병렬 요청 동시 만료) 먼저 도착한 요청이 토큰을 회전시키고, 뒤에 온 요청은 방금까지 유효했던 토큰을 들고 와서 불일치 판정을 받는다. 단일 세션 설계라 곧 전 기기 로그아웃이다. 재발급 경합은 버그가 아니라 흔한 동시성이고 서버가 프론트의 요청 순서를 통제할 수 없다. `GET → 비교 → SET`이 원자적이지 않아 같은 레이스가 한 층 위에서도 발생했다.
- **후보**:
  - 클라이언트가 refresh를 직렬화(mutex) — 서버 코드 0줄
  - grace 윈도우 — 직전 토큰을 짧은 시간 허용 (선택)
  - 회전 자체를 제거 — refresh를 TTL까지 고정
  - 재사용 감지는 유지하되 세션 삭제만 제거
- **선택**: grace 윈도우 10초. Redis 키 두 개(`REFRESH_TOKEN:USER:{publicId}` 세션, `REFRESH_GRACE:{제시된토큰}` 마커)를 Lua 스크립트 하나로 원자적으로 다룬다(`src/main/resources/scripts/refresh-rotate.lua`, `RefreshTokenRepository.GRACE_TTL`). grace에 걸린 요청에는 **새 토큰을 발급하지 않고 현재 세션 토큰을 그대로** 돌려준다.
- **이유**: 오탐과 탈취 감지를 둘 다 지키는 유일한 안이다. 회전을 없애면 탈취된 refresh가 14일 내내 살아 있어 회전의 이점을 통째로 버리게 되고, 즉시 무효화는 정상 사용자를 끊는다. 클라이언트 직렬화는 서버의 안전을 통제 못 하는 쪽(웹뷰·여러 탭·재설치)에 의존하게 된다. 같은 토큰을 돌려주는 것이 핵심인데, 새 토큰을 주면 클라이언트들이 서로 다른 토큰으로 갈라져 grace가 끝나는 순간 한쪽이 죽는다. 같은 값으로 수렴시켜야 회전이 멱등해진다. grace 창은 "실제 공격은 보통 10초 뒤에 온다"는 가정 위에서 둘을 절충한 것이다.
- **포기한 것**:
  - **탈취 감지가 10초 무뎌진다.** 정상 사용자가 회전시킨 직후 10초 안에 공격자가 옛 토큰을 쓰면 감지되지 않고 현재 토큰을 받는다. 그것도 한 번이 아니라 **10초 동안 횟수 제한 없이** 통한다 — grace 마커는 EXISTS로만 확인되고 소비되지 않기 때문이다.
  - 동시 재발급 간격이 10초를 **넘으면** 다시 오탐이 난다. 그 구간은 서버가 닫지 못하므로 프론트가 재발급을 직렬화해야 한다. 창 안쪽 경합은 Lua가 처리하므로 프론트 규약 의존은 "창을 넘길 때"로 한정된다.
  - Redis 상태가 하나 늘고, 회전 로직이 Java가 아니라 Lua에 있다. **스크립트의 판정 로직은 자동 테스트가 없다** — 저장소 테스트는 키와 ARGV(제시 토큰·후보 토큰·세션 TTL 초·grace TTL 초)를 옳게 넘기는지, 응답 문자열을 레코드로 바꾸는지, 모르는 상태 문자열을 예외로 막는지만 본다. 실제 Redis가 있어야 검증되는데 Testcontainers는 `./gradlew test`에 Docker를 요구해서 도입하지 않았다. 대신 `redis-cli --eval`로 손 검증한다.
  - grace로 응답할 때 refresh 쿠키의 Max-Age가 후보 토큰 기준(14일)이라 실제 잔여 수명보다 최대 10초 길다.
  - 후보 JWT를 미리 만들어 스크립트에 넘기므로, 경합에서 진 요청의 JWT는 버려진다.
- **다시 볼 시점**: **재사용 감지 로그를 세는 것이 이 결정을 다시 볼 유일한 근거다.** 정상 사용자에게서 자주 뜨면 창을 늘리고, 프론트가 직렬화한 게 확인되면 줄이거나 없앤다. 10초가 짧아 오탐이 남으면 창을 늘리기 전에 클라이언트의 refresh 동시성부터 확인할 것. 다중 세션(기기별 로그인)으로 가면 세션 키가 publicId 하나가 아니게 되어 스크립트를 다시 설계해야 한다. Redis Cluster로 가면 세션 키와 grace 키가 다른 슬롯에 떨어져 한 스크립트로 다룰 수 없다(해시 태그 필요).

## 2026-08-14 — 소셜 계정과 로컬 계정을 별개 계정으로 둔다

- **배경**: `user@example.com`으로 하루컷 가입을 한 사람이 나중에 같은 이메일의 구글 계정으로 로그인하면 어떻게 되어야 하는가. 기존 Kotlin 구현은 별개 계정이었다.
- **후보**:
  - 별개 계정 — provider가 다르면 다른 사용자 (선택)
  - 이메일이 같으면 자동으로 같은 계정에 연결
  - 로그인 후 사용자가 직접 연결(link)하는 화면 제공
- **선택**: 별개 계정. 유니크 제약을 `(provider, email)`과 `(provider, provider_id)`로 걸어 **스키마 수준에서 별개임을 고정**했다(`User` 엔티티).
- **이유**: 자동 연결은 "이 이메일의 소유자가 맞다"를 제공자 말만 믿고 판단하게 된다. 제공자가 미인증 이메일을 주거나 `email_verified`를 안 주면, 남의 로컬 계정을 이메일만 알고 탈취할 수 있는 경로가 생긴다. 직접 연결은 안전하지만 연결 해제·중복 로그인 수단 관리 화면이 따라붙는다. 지금 규모에 과하다.
- **포기한 것**: **사용자가 로그인 수단을 헷갈리면 "내 데이터가 사라졌다"고 느낀다.** 계정이 둘로 갈리면 프레임·구독·결제 이력이 각각 쌓이고, 나중에 합치려면 **두 계정의 데이터를 어떻게 병합할지부터** 정해야 한다 — 결제가 붙은 뒤에는 특히 비싸진다. 지금은 프론트가 "이 이메일은 구글로 가입되어 있습니다" 같은 안내를 할 근거가 없다(어느 provider로 가입했는지 알려주는 API가 없다). 다만 **로컬 가입 여부 자체는 이미 샌다** — 인증 없이 열린 `/api/email-auth/code`가 로컬(HARUCUT) 계정이 있으면 `AUTH-005 EMAIL_ALREADY_IN_USE`를 돌려준다. 즉 "이메일 존재 여부가 새어 나간다"는 것은 이 결정이 막고 있는 것이 아니다.
- **다시 볼 시점**: "로그인은 되는데 데이터가 없다"는 CS가 쌓이면. **재검토 조건이었던 "결제 붙기 전"은 이미 지났다** — 결제·구독이 붙은 상태에서 계정 분리를 유지하기로 했다면 그 판단을 새 항목으로 남겨야 한다.

## 2026-08-14 — 소셜 로그인 결과를 쿠키 + 302 리다이렉트로 전달한다

- **배경**: 제공자 콜백(`/login/oauth2/code/{provider}`)을 처리한 뒤 프론트에 로그인 완료를 어떻게 알릴 것인가. 로컬 로그인은 JSON 응답인데 여기만 형태가 다르다.
- **후보**:
  - 토큰 쿠키 2개를 붙이고 `{frontend}/oauth2/callback`으로 302 (선택)
  - 일회용 code를 쿼리로 넘기고, 프론트가 그 code를 토큰으로 교환하는 엔드포인트를 호출
- **선택**: 쿠키 + 302 (`CustomOAuth2SuccessHandler`).
- **이유**: **콜백 요청의 주체가 우리 프론트 JS가 아니라 브라우저 자체다.** 제공자가 브라우저를 우리 서버로 돌려보낸 결과이므로, JSON을 응답하면 사용자 화면에 JSON 텍스트가 그대로 뜬다. 받아서 처리할 코드가 그 자리에 없다. code 교환 방식은 그 문제를 우회할 수 있지만 교환 엔드포인트와 code 저장소(Redis 키)가 추가로 필요하다. 기존 Kotlin 구현도 이 방식이고 프론트가 이미 그 형태로 동작한다.
- **포기한 것**: **쿠키가 실린다는 전제에 묶인다.** 프론트와 API가 서로 다른 등록 가능 도메인에 배포되면 쿠키가 안 실려 로그인이 통째로 깨진다. 쿠키를 못 쓰는 클라이언트(모바일 앱)도 이 경로를 못 탄다. 그리고 **실패 이유를 세밀하게 전달할 수 없다** — 리다이렉트 URL은 브라우저 기록·Referer에 남으므로 `?error=oauth2` 하나로 뭉갠다. 사용자는 왜 실패했는지 알 수 없다.
- **다시 볼 시점**: 프론트를 API와 다른 등록 가능 도메인에 배포하기로 하면. 또는 모바일 앱이 붙을 때. 둘 중 하나라도 생기면 code 교환 방식이 사실상 강제된다.

## 2026-08-16 — 약관 저장 구조: append-only 단일 이력 대신 "현재 1행 + 이력 로그" 이원화

- **배경**: 기존 Kotlin 구현은 동의를 `TermsConsent` 한 테이블에 append만 한다. 현재 상태는 **사용자의 전체 동의 행을 `createdAt DESC`로 통째로 읽어와 서비스 계층에서 약관 코드로 groupBy 후 첫 행을 고르는** 방식으로 계산하고, 최신 버전 조회는 상관 서브쿼리(`MAX`)를 쓴다. 재구현하면서 이 "그룹별 최신 1건" 패턴이 조회마다 반복되는 것이 이해·유지보수 부담으로 판단됐다.
- **후보**:
  - Kotlin 그대로 — append-only 단일 테이블 + 상관 서브쿼리 1곳(최신 버전) + 서비스 계층 메모리 groupBy 1곳
  - 개정 시 옛 버전 행을 보관 테이블로 옮기기
  - "현재"를 별도 행으로 실체화 — 버전은 약관당 1행 포인터(`current_terms_version`), 동의는 사용자×약관당 1행(`terms_agreement`, unique) + append 전용 로그(`terms_agreement_history`) (선택)
- **선택**: 실체화. 이력 로그는 FK 없이 값만 담는다(불변인 `code`를 스냅샷으로 포함). 읽는 곳은 관리자 증빙 API 하나뿐이다.
- **이유**: 상관 서브쿼리와 메모리 groupBy가 전부 사라지고, 모든 조회가 "현재 행에서 출발해 조인"으로 단순해진다. "약관당 현재 버전 1개", "사용자×약관당 동의 1행"이 코드가 아니라 **unique 제약으로** 보장된다. 보관 테이블 이동은 행이 이동하는 순간 그 행을 가리키던 동의 기록의 FK가 깨져서 탈락. 법적 증빙은 로그 테이블이 그대로 담당한다 — code가 불변이라 스냅샷이 낡지 않는다. 상태(AGREED 등)는 여전히 저장하지 않고 조회 시점에 계산한다. 그건 이 결정과 별개로 유지.
- **포기한 것**: **쓰기가 "insert 한 번"에서 "여러 곳 동기화"로 바뀐다.** 동의는 agreement 갱신 + history append를 항상 짝으로 해야 하고, 개정은 버전 insert + 포인터 repoint를 잊으면 안 된다. append-only에는 존재하지 않던 **동시 insert 경쟁**이 생겼다 — 같은 사용자가 동의를 동시에 두 번 보내면 둘 다 "행 없음"을 읽고 insert를 시도, unique 위반으로 한쪽이 500을 받는다(데이터는 안 깨진다. UX만 나쁘다). 개정도 같은 모양의 동시성 문제가 있다. 그리고 상태 조회가 이력을 안 보므로, agreement와 history가 어긋나는 버그는 **조회로는 발견되지 않는다.**
- **다시 볼 시점**: 동의 더블클릭 500이 실제 로그에 잡히면 (그때 unique 위반을 잡아 재시도/무시 처리). agreement와 history가 어긋난 사례가 나오면 — 그땐 둘을 대조하는 정합성 점검부터. **탈퇴 삭제 정책은 이미 정해졌다** — `TermsAgreementDeletionHandler`가 `terms_agreement`와 `terms_agreement_history`를 **둘 다 물리 삭제한다.** 증빙 이력을 남기지 않는 쪽을 택한 셈이라 위 "법적 증빙은 로그 테이블이 담당한다"와 상충한다. **그 판단의 근거를 별도 결정으로 기록해야 한다.**

## 2026-08-16 — 스토리지: 범용 파일 API 축소 + 업로드 크기를 서명으로 강제

- **배경**: 기존 Kotlin의 파일 API 3종(presigned-upload / presigned-img / delete) 중 **조회와 삭제에 소유권 검증이 전혀 없었다** — key만 알면 남의 사진을 보고 지울 수 있다(IDOR). 업로드는 **크기 제한이 없었다** — presigned PUT은 서버를 거치지 않아 서버 코드로는 못 막는다. 삭제는 S3 객체만 지우고 DB 참조는 남겨 깨진 참조도 만들었다.
- **후보**:
  - Kotlin 그대로 (검증 없음)
  - 세 API 전부 유지 + 소유권 검증만 추가
  - **delete 제거** + presigned-img는 내 prefix만 + 업로드 요청에 `fileSize`를 받아 Content-Length를 서명에 포함 (선택)
- **선택**: delete 제거 + 나머지 둘에 소유권 기준선. 기준선은 `S3Keys.userRoot()` 한 곳에만 두고(전략의 key 생성과 검증이 같은 메서드), 검사는 **사용자 입력 key가 처음 들어오는 공개 API 경로에서 한 번만** 한다 — 내부(도메인 서비스)는 시스템 프레임처럼 남의 key를 정당하게 presign하는 경로가 있어서 거기에 넣으면 안 된다. 실제 검사 지점은 둘이다: presigned-img는 컨트롤러(`FileController.verifyOwnership`), 프로필 변경은 서비스(`UserService.changeProfileImage`). 프로필 쪽은 **정규화 후에** 검사한다(URL로 감싼 남의 key가 원본 문자열 검사는 통과한다).
- **이유**: 삭제는 검증을 추가해도 **자기 파일을 지워 깨진 참조를 만드는 문제**가 남는다 — 파일 생명주기는 그 파일을 참조하는 도메인 API가 소유해야 안전하다. 크기 제한은 Content-Length를 서명에 넣는 것이 presigned PUT을 유지하는 유일한 서버 측 강제 수단이다(S3가 서명 불일치로 거부). presigned POST + policy는 범위 제한이 되지만 업로드 방식 자체가 바뀌고 Java SDK v2가 policy 서명을 지원하지 않는다.
- **포기한 것**: **프론트가 파일을 직접 지울 수단이 없다** — "올렸는데 등록 안 한" 고아 객체는 그대로 쌓이고, 정리는 S3 Lifecycle 정책 몫인데 **아직 도입 안 했다.** 업로드는 `fileSize`를 정확히 신고해야 해서 프론트 계약이 복잡해졌고(발급 후 파일 교체 불가), 남은 두 API 모두 기존 Kotlin과 응답 계약이 어긋난다 — **다만 그 변경 내역이 아직 `frontend-changes.md`에 기록되지 않았다**(현재 1·2번 두 항목뿐, 기준일 2026-08-12). 옛 프로필 이미지의 S3 객체도 아직 안 지운다 — 고아가 하나 더 쌓인다.
- **다시 볼 시점**: **S3 삭제 시점은 정해졌다** — AFTER_COMMIT 이벤트로 미룬다(아래 2026-08-17 항목). 탈퇴 경로는 그 패턴에 합류했지만 `S3Deleter`를 우회해 이벤트를 직접 발행하고, **프로필 이미지 "변경" 시 옛 객체 삭제는 여전히 미구현 이월 항목이다.** **네컷 업로드 타입 재설계도 끝났다** — 완성본 업로드 타입은 없애고 `FOURCUT_SOURCE`(원본 전용) 하나만 남겼으며 결과물 key는 서버가 만든다. 버킷 용량에서 고아 객체가 실제로 보이기 시작하면 Lifecycle 정책을 그때는 미루지 않는다.

- **포기한 것**: 사용자 응답에서 "원래 결제했던 등급" 정보(재구독 유도 안내 불가 — 필요해지면 필드 추가). 관리자의 등급 강제 변경 수단(`PATCH /plan` 제거 — 무기한 등급 백도어라서).

PAST_DUE 마지막 재청구가 먼저 돌고 실패한 것만 강등되도록 순서를 잡았다. 이벤트 기반 후보는 채택하지 않았다. **수동 등급 부여 공백도 쿠폰 도메인으로 해소됐다** — 관리자가 `CouponAdminController`로 부여하고, 유료 구독 중이면 `reservedUserCouponId`로 예약되어 만료 배치가 활성화한다. **갱신 청구의 전달 보장도 결론이 났다** — RabbitMQ·아웃박스 없이 Spring Batch 잡을 매일 02:00에 기동한다(아래 «기록 후보» 참조).

## 2026-08-16 — 구독: 도메인 간 결합을 포트 두 방향으로 차단

- **배경**: 프레임·미디어는 구독 정책(한도·보관 기간)이 필요하고, 구독 사용량은 프레임 개수가 필요하다. 기존 Kotlin은 정책 쪽만 포트로 지키고(`frame/policy` 인터페이스), 사용량은 `FrameRepository`를 직접 import해서 subscription→frame 구체 의존을 만들었다. 우리는 frame 도메인이 아직 없어서(Phase 8) 그 방식으로는 사용량을 만들 수도 없었다.

  - 전부 직접 import (가장 단순, 결합 수용)
  - 정책만 포트 (Kotlin)
  - 양방향 포트 — 정책은 frame/media가 선언, 프레임 개수는 subscription이 선언 (선택)
  - user/info의 등급·가격 접근까지 포트화

- **이유**: frame 부재 상태에서 사용량 기능을 완성할 수 있었고(포트+임시 어댑터), Phase 8~9의 frame·media가 subscription 내부를 모른 채 개발된다. Kotlin의 Clock 미경유 버그도 이 재작성에서 함께 고쳤다 — `resolveHistoryCutoff`뿐 아니라 `assertHistoryAccessible`에도 맨 `LocalDateTime.now()`가 있었고, Java는 등급 판정(`resolvePolicy`)까지 세 곳 모두 `LocalDateTime.now(clock)`으로 통일했다.
- **포기한 것**: user↔subscription 패키지 순환(수용 — 빈 순환은 아님), 구현 추적의 간접성 한 단계, 임시 어댑터 교체를 잊을 위험(잊으면 빈 충돌로 기동이 죽으므로 조용히 잘못되진 않는다). 그리고 **이 포트가 막는 것은 엔티티 레벨 결합까지다** — 서비스 계층은 뚫려 있다. `frame`은 `SubscriptionErrorCode`를 직접 import해 소프트 캡 초과를 스스로 던지고(`FrameService.assertWithinRetentionCap`), `subscription`은 `coupon`(`GrantActivationService`)과 `payment`(`BillingKeyRepository`)를 직접 import한다. `media`만 subscription을 전혀 import하지 않는다.
- **다시 볼 시점**: **임시 어댑터는 예정대로 제거됐다** — `FrameCountPort`의 구현은 `frame/adapter/FrameCountAdapter` 하나다(삭제 커밋 `4124886`). 남은 재검토 사유는 훗날 모듈 분리를 하게 될 때 인터페이스를 공유 모듈로 옮길지 하나뿐이다.

## 2026-08-17 — 프레임: S3 파일 삭제는 커밋 후에만 실행한다 (AFTER_COMMIT 이벤트)

- **배경**: 프레임 수정·삭제가 저장소 둘을 건드린다 — DB(행)와 S3(파일). DB는 롤백이 되지만 S3 삭제는 되돌릴 수 없다. Kotlin은 트랜잭션 중간에 즉시 삭제해서(`harucut_ktl_be`의 `FrameServiceImpl.kt:106-120`), 이후 커밋이 실패하면(제약 위반·`@Version` 충돌·커넥션 끊김) DB는 옛 상태로 돌아가는데 파일만 사라진다 — 저장된 프레임의 이미지가 깨지는, 사용자에게 보이는 복구 불가 장애.
- **후보**:
  - 커밋 전 즉시 삭제 (Kotlin 현행)
  - `@TransactionalEventListener(AFTER_COMMIT)`로 커밋 후 삭제 (선택)
  - 지금은 안 지우고 참조 스캔 배치 GC
- **선택**: AFTER_COMMIT. `S3DeleteEvent`(지울 key의 불변 스냅샷, storage 소유) + `S3DeleteListener`(AFTER_COMMIT, key 단위 best-effort). 거르기(null·비관리 key·중복)와 이벤트 발행은 storage의 공용 부품 `S3Deleter.deleteAfterCommit(Collection<String>)`이 한다.
- **이유**: 실패 방향의 비대칭. "지웠는데 롤백"은 깨진 화면(가시·복구 불가), "커밋했는데 삭제 실패"는 고아 파일(비용·비가시·나중에라도 지울 수 있음). 되돌릴 수 없는 일은 되돌릴 수 있는 일이 전부 확정된 뒤에 한다. 이 장치는 storage에 있어 어느 도메인이든 재사용한다 — 실제로 미디어(`UserMediaService`·`ComposeService`)와 프레임(`FrameService`·`FrameAdminService`·`FrameComponentAssembler`·`FrameUserDeletionHandler`)이 쓴다.
- **포기한 것**: 삭제의 전달 보장 — AFTER_COMMIT 이벤트는 메모리에만 있어 커밋 직후 서버가 죽으면 유실된다(고아 파일 잔존). 아웃박스(지울 key를 DB에 적고 배치가 지움)로 막을 수 있지만, 고아 파일 몇 개의 스토리지 비용에 그 인프라는 과하다 — 잃는 것의 크기가 보장의 비용을 결정한다(갱신 청구와 대비). 리스너가 예외를 key 단위로 삼키므로("저장은 됐는데 500" 방지) 삭제 실패는 로그로만 보인다. 그리고 **진입점이 하나로 모이지 않았다** — `FrameAssetManager.deleteAfterCommit`은 프레임 쪽 얇은 위임이고 media는 `S3Deleter`를 직접 쓰는데, `UserExitService`만 `S3Deleter`를 우회해 `ApplicationEventPublisher`로 `S3DeleteEvent`를 직접 발행한다.
- **다시 볼 시점**: 고아 파일 스토리지 비용이 눈에 띄기 시작하면(참조 스캔 GC를 보조로 추가). 트랜잭션 없는 경로에서 `deleteAfterCommit`을 부르는 코드가 생기면 — `fallbackExecution` 기본값(false) 때문에 리스너가 조용히 안 불린다. **이 조용한 실패를 잡는 테스트는 지금 없다** — `S3DeleteFlowTest`가 고정하는 것은 "커밋 후에만 지워지고 롤백이면 안 지워진다"는 의미론이고, 그 테스트는 경계를 스스로 만들기 때문에 서비스에서 `@Transactional`이 빠져도 통과한다. 실질적 방어선은 `S3Deleter`·`S3DeleteListener`의 주석뿐이다.

## 2026-08-17 — 네컷 합성을 프론트에서 백엔드로 옮긴다 (텍스트는 프론트가 굽고, 실행은 Lambda)

- **배경**: 기존 Kotlin 구조는 프론트가 canvas로 네컷을 합성해 완성본을 presigned로 올리고, 서버는 등록만 받았다. 서버는 올라온 파일이 진짜 네컷인지 모르고, 등록 API에는 소유권 구멍(남의 s3Key 등록)과 멱등 문제가 있었으며, 저사양 폰이 6000×4000 캔버스를 그리는 부담도 프론트 몫이었다. Phase 6에서 `FOURCUT_PHOTO` 업로드 타입을 미리 제거하며 방향은 정했고, 이번에 비용을 전부 올려놓고 확정했다.
- **후보**:
  - 프론트 합성 유지 — 등록 API 부활 + 그 API의 멱등·소유권 문제를 다시 풀기
  - 백엔드가 렌더러 전체를 재구현 — 배경·사진·스티커·텍스트 전부 (폰트 포함)

- **선택**: 텍스트를 프론트가 굽는 안 + Lambda + 폴링. **어디서 실행할지**는 `ComposeExecutor` 인터페이스가 가른다 — 로컬·테스트는 `InProcessComposeExecutor`(Java2D), 운영은 `LambdaComposeExecutor`, `compose.executor` 프로퍼티로 선택. **무엇을 그릴지**는 인터페이스가 아니라 구상 클래스 `FourcutRenderer`(compose-core)가 서버·Lambda 양쪽에서 그대로 재사용된다 — 갈아끼우는 지점은 실행 위치뿐이고 그리기 코드는 한 벌이다. 서버가 백그라운드 스레드에서 Lambda를 **동기** 호출하므로 호출 응답이 곧 완료 통지다(콜백 엔드포인트·큐 불필요). 프론트는 202 + jobId를 받고 상태를 폴링한다. 작업은 Job 행(PENDING/DONE/FAILED)으로 기록한다. 중복 합성은 클라이언트 멱등 key + unique 제약으로 막는다. 원본 4장은 합성 성공 시 삭제(`S3Deleter`). 프론트 코드 조사(harucut_FE) 후 추가 확정: **슬롯 좌표는 FrameType별로 서버가 소유**하고 스펙에 숫자를 실어 보낸다(Lambda 자체 상수 금지 — 배포물 둘에 숫자 두 벌 방지. 프론트는 웹·모바일에 이미 두 벌 하드코딩돼 있었다). 좌표계는 출력 픽셀 1:1, 사진은 cover(비율 유지+중앙+클리핑). **사진 필터(흑백/밝게/뽀샤시)는 프론트가 원본에 구워 올린다** — 서버는 필터를 모른다. **셀 누끼(비네트 장식)는 Frame에 cellCutouts로 영속화**하고 합성기가 그린다 — 서버가 직접 그리는 유일한 효과. 파라미터가 고정 숫자(그라디언트 색·반경 비율)라 텍스트와 달리 재현 위험이 낮고, 프론트 ADR-0002의 알려진 한계(저장 프레임 재사용 시 누끼 소실)도 이 필드로 해결된다.
- **이유**: 합성을 서버가 소유하면 "아무 이미지나 네컷으로 등록"이 불가능해지고 등록 API가 통째로 사라진다. 렌더러 이중 구현의 진짜 위험은 텍스트 하나였다 — 사진·스티커는 이미 그림이라 얹기만 하면 되지만, 텍스트는 DB에 글자+스타일로 저장돼 있어 서버가 폰트로 다시 그려야 하고, 브라우저와 자바는 같은 폰트로도 글자 폭을 다르게 계산한다(이모지는 자바 기본 렌더러가 아예 못 그림). 프론트가 구우면 사용자가 편집 화면에서 본 픽셀이 그대로 결과물에 들어가 WYSIWYG 어긋남이 원천 소멸한다. 합성 한 건이 메모리 ~96MB(6000×4000×4byte)를 몇 초 무는데, Lambda는 건당 실행 환경을 띄워 자동 확장하고 사용량 과금이라 이 부담이 서버 밖으로 나간다. SQS를 안 쓴 이유: 큐는 멱등을 주지 않고(최소 1회 전달이라 오히려 중복 가능), 유실 3지점(호출 전 서버 사망 / Lambda 사망 / 결과 전달) 중 마지막만 지키며, 나머지를 치울 장치는 어차피 필요하다.
- **포기한 것**: **프론트 계약이 늘었다** — 텍스트 층을 출력 해상도로 구워 컴포넌트마다 하나 더 업로드해야 하고, 글자·스타일 원본과 구운 그림이 두 벌이라 저장 때 같이 굽지 않으면 어긋난다(어긋나도 서버는 모른다). **배포물이 둘이다** — 좌표 해석이 바뀌면 서버와 Lambda를 같이 고쳐야 한다. Lambda **핸들러 코드** 자체는 로컬 테스트에 잡히지만(`ComposeHandlerTest`가 목 S3Client로 payload 파싱·다운로드·업로드를 검증) 그 바깥(실제 런타임 배포·IAM 역할·`LambdaComposeExecutor`의 실제 invoke 경로)은 안 잡힌다. **결과가 즉시가 아니다** — 폴링 + 콜드 스타트 포함 수 초 걸린다. **재합성 불가** — 원본을 지우므로 같은 사진을 다른 프레임으로 다시 만들려면 재업로드해야 한다(필터도 구워서 올리므로 무필터 원본은 서버에 아예 없다). 비네트 그리기 코드는 프론트(미리보기)와 서버(합성) 두 벌이다.
  - **✅ 2026-08-21 해소.** 이 결정이 기대고 있던 재실행 장치를 구현했다 — `started_at` 컬럼과 조건부 UPDATE 선점(`ComposeJobRepository.claim`), 30초 주기 `ComposeRerunScheduler`, 그리고 graceful shutdown 설정. 이제 Job 테이블이 실제로 큐다: 큐 거부·서버 재시작·실행자 사망 어느 쪽으로 버려져도 오래된 PENDING을 다시 집어간다. 실측으로 동시 30건에서 26건이 영구 PENDING이던 것이 0건이 되었다(`monitoring/01-test-targets.md` #1). **다만 "결과 전달"은 여전히 동기 호출에 의존한다** — 비동기 invoke로 바꾸면 이 결정을 다시 봐야 한다.

## 2026-08-17 — 네컷 썸네일을 합성 시점에 함께 만든다 (온디맨드 리사이즈 대신)

## 2026-08-18 — 결제 멱등 키: 클라이언트 생성 + 결과 재생

- **배경**: 결제 버튼 이중 클릭이나 네트워크 재전송으로 같은 결제가 두 번 실행되는 것을 막아야 했다. 기존 Kotlin 구현의 키는 `initial:{userId}:{랜덤}`이라 요청마다 달라서 이름만 멱등 키였다 — 두 번 누르면 두 번 결제된다.
- **후보**:
  - Kotlin 그대로 (랜덤 키) — 멱등성 없음
  - 결정적 서버 키 (`initial:{userId}:{planTier}`) — 실패한 주문이 유니크 제약을 계속 차지해 재시도가 막힌다
  - 클라이언트 생성 키 + 중복이면 409 거부
  - 클라이언트 생성 키 + 결과 재생 (선택)
- **선택**: 클라이언트가 결제 시도마다 키를 만들어 보낸다(`SubscribeRequest.idempotencyKey`). 같은 키가 다시 오면 그 키로 만들어진 주문의 상태를 보고 **첫 요청의 결과를 재생**한다 — PAID면 200 + 현재 구독 상태, FAILED면 같은 402, 결과 미확정(CREATED·IN_PROGRESS)이면 409. 키가 같아도 사용자·planTier가 다르면 재생하지 않고 409. 경쟁 요청은 `payment_order`의 멱등키 유니크 제약이 최후 방어선이고, 주문 커밋이 청구보다 앞에 있어서 중복 청구는 구조적으로 불가능하다.
- **이유**: 응답을 못 받고 끊긴 클라이언트가 같은 키로 다시 물으면 결과를 받아가는 게 진짜 멱등이다. 별도의 응답 저장소 없이 주문 상태(CREATED/IN_PROGRESS/PAID/FAILED)가 곧 결과의 기록이라 재생이 싸게 된다. `IN_PROGRESS`는 갱신 배치가 PG 호출 직전에 찍는 도장이라 초기 결제 주문에는 나오지 않지만, 재생 분기는 CREATED와 같은 "결과 미확정"으로 묶어 처리한다.
- **포기한 것**:
  - 원본 응답이 아니라 **현재 구독 상태**를 재생한다. 첫 응답과 재생 응답이 완전히 같다는 보장은 없다(그 사이 해지했으면 CANCELED로 보인다).
  - 커밋 #1과 #2 사이에 서버가 죽으면 주문이 CREATED로 남아 그 키는 영원히 409다. 돈이 빠졌는지도 모른다. 실 PG의 웹훅/조회 연동 전까지는 수동 확인 대상.
  - **"중복 청구는 구조적으로 불가능"이 커버하지 않는 범위가 하나 있다.** 같은 키로 동시 요청이 들어오면 진 쪽은 유니크 제약에서 막혀 DB가 롤백되지만, **빌링키 발급 PG 호출은 이미 마친 뒤**라 PG 쪽에 고아 빌링키가 남는다.
  - 클라이언트가 규칙을 지켜야 한다: 재전송은 같은 키, **새 시도는 새 키**. 프론트가 키를 재사용하면 새 결제가 계속 402/409로 막힌다.

- **다시 볼 시점**: 실 PG 연동 시 CREATED 고아 주문을 웹훅/조회로 복구하는 로직을 넣을 때. **정기결제 키와의 관계는 확인됐다** — 갱신 주문도 같은 `payment_order` 테이블·같은 유니크 제약을 쓰고, 갱신 키 `renewal:{subscriptionId}:{yyyyMMdd}`는 `renewal:` 접두사로 네임스페이스가 분리되어 클라이언트 생성 키와 충돌하지 않는다. 조회 방식은 다르다 — 갱신 쪽은 재생 대신 `existsByIdempotencyKey`로 존재만 보고 건너뛴다. 응답 원문 보존이 필요해지면(영수증 등) 재생 방식 전체 재검토.

## 2026-08-18 — 구독이 빌링키를 참조하지 않는다

- **배경**: 결제 성공 시 구독을 활성화한다. 기존 Kotlin은 `UserSubscription.activatePaid(..., billingKey)`로 구독 엔티티가 BillingKey를 FK로 직접 참조한다. 이 결합을 따라갈지 정해야 했다.
- **후보**: Kotlin처럼 구독→빌링키 참조 / 참조 없이 userId로 조회
- **선택**: 참조하지 않는다. `activatePaid`는 tier와 기간만 받는다. 빌링키가 필요한 곳은 `BillingKeyRepository.findAllByUserIdAndStatus(userId, ACTIVE)`로 찾는다 — 소비처는 셋이다(정기결제 준비/청구 배치, 새 키 발급 시 옛 키 정리, 구독 만료 시 카드 정리). 대신 **새 키 발급 시 그 사용자의 옛 ACTIVE 키를 전부 DELETED로 바꾸는 규칙**으로 "ACTIVE는 항상 1개"를 유지한다(`PaymentTransactionService.createInitialOrder`).
- **이유**: 엔티티 레벨 FK를 두면 구독 행의 수명주기가 카드 행에 묶인다. 카드를 지우거나 교체할 때 구독 행까지 건드려야 하고, 되돌리려면 두 도메인의 스키마가 같이 움직인다.
  > ⚠️ 원래 이 결정의 근거는 "subscription 패키지가 payment를 import하지 않게 한다"였는데 **그 근거는 더 이상 성립하지 않는다.** `SubscriptionExpirationService`가 payment 패키지의 `BillingKey`·`BillingKeyStatus`·`BillingKeyRepository`를 직접 import한다. "frame/media가 subscription을 모르게 지켜온 단방향 원칙"도 사실이 아니다 — frame과 subscription은 서로를 import한다(포트 구현 방향과 정책 타입 사용 방향이 공존). 지금 남아 있는 실익은 **엔티티 레벨 FK가 없다는 것 하나**다.
- **포기한 것**:
  - "이 구독이 어느 카드로 갱신되는가"를 구독 행만 보고는 알 수 없다 — 조회가 한 번 더 필요하다.
  - ACTIVE 1개 규칙이 어떤 경로로든 깨지면 갱신 배치가 어느 키를 쓸지 모호해진다. 발급 코드가 옛 키를 전부 정리하는 방식(규칙을 믿지 않고 복구)으로 방어하지만, **ACTIVE가 2개 이상이면 `get(0)`이 임의 선택이다.**
  - 카드 여러 장 등록 후 선택 같은 기능이 생기면 이 구조로는 부족하다.
- **다시 볼 시점**: **`(userId, ACTIVE)` 조회로 충분한지는 확인됐다** — 키가 없는 경우는 준비 단계에서 `markPastDue`, 청구 직전 소실은 시도 없이 `markFailed`+`markPastDue`로 처리한다. 남은 미해결은 위의 `get(0)` 하나다. 빌링키 조회/교체/삭제 API(카드 관리)를 만들 때 다시 본다.

## 2026-08-18 — 쿠폰 사용 상한 동시성: 조건부 UPDATE + 카운터 컬럼

- **배경**: 사용 상한이 있는 쿠폰에 동시 요청이 오면 "카운트 조회 → 저장"이 두 문장이라 상한이 뚫린다. 기존 Kotlin 구현이 이 상태다(상한 1에 동시 10명이면 성공이 2건 이상 가능).
- **후보**: 조건부 UPDATE + 카운터 비정규화 / 비관적 락(`SELECT FOR UPDATE`) / Redis 카운터
- **선택**: `Coupon.redeemedCount` 컬럼 + 조건부 갱신(`tryIncrementRedeemedCount`). WHERE 절은 `c.id = :couponId AND (c.maxRedemptions IS NULL OR c.redeemedCount < c.maxRedemptions)` — 상한이 null이면 조건이 항상 참이라 무제한으로 증가한다. 갱신된 행이 0이면 매진(COUPON-005). 서비스에는 빠른 거절용 read 검사(문앞)와 이 관문의 이중 구조를 둔다.
- **이유**: 검사와 증가가 DB 한 문장이라 그 사이에 끼어들 틈이 없다. UPDATE가 자동으로 거는 행 락을 그대로 쓰므로 명시적 락보다 락 보유 시간이 짧다. 부가 효과로 관리자 목록의 사용 수가 컬럼 읽기로 끝나 집계 쿼리(GROUP BY)와 매칭 코드가 사라진다. Redis는 DB 롤백과 카운터가 어긋나는 보정 문제가 있어 이 규모엔 과하다.
- **포기한 것**:
  - **진실이 2개가 된다**(이력 행 수 vs 카운터). 한 요청 안에서는 같은 트랜잭션이라 롤백이 함께 되지만, **정상 운영 경로에서도 어긋난다** — 회원 탈퇴 시 `CouponUserDeletionHandler`가 `user_coupon` 행만 삭제하고 `redeemedCount`는 감소시키지 않는다. 즉 탈퇴해도 상한 슬롯은 영구 소모된다.
  - 이 UPDATE는 영속성 컨텍스트를 비우므로(`clearAutomatically`), 이후 수정할 엔티티는 반드시 관문 뒤에 읽어야 한다는 순서 제약이 서비스 코드에 생겼다.
- **다시 볼 시점**: 위의 탈퇴 시 카운터 미복구를 고칠 때 — 상한을 되돌릴 것인지(감소), 소모로 둘 것인지(현행)를 명시적으로 정해야 한다. 같은 패턴이 다른 도메인에 반복 등장해 일반화가 필요할 때.

## 2026-08-21 — 합성 Lambda 호출을 비동기로 바꾸고, 결과는 Destinations → SQS로 받는다

- **배경**: 8/17 결정은 "동기 호출의 응답이 곧 완료 통지"라는 전제 위에 서 있었다. 그 전제의 비용을 이번에 실측했다 — Lambda를 실제로 배포하고(2048MB / 60초 / x86_64) 실사진 4장짜리 Job 18건을 `core` 2·10·30으로 던졌다(`monitoring/01-test-targets.md`). 세 가지가 드러났다. ① **합성 1건이 8.3초고 그중 7.9초가 Lambda 안**이다(CloudWatch `Duration`) — 우리 스레드는 소켓에서 자기만 한다. 처리량이 정확히 `core ÷ 8.3`으로 나왔다(core 2 → 실측 75.5초 / 이론 74.7초, core 10 → 19.4초). ② 병목은 우리 코드가 아니라 **Lambda 동시 실행 한도**였다(이 계정 `ConcurrentExecutions: 10`). DB 커넥션도 CPU도 힙도 아니었다. ③ 그 한도를 넘기면 동기 invoke는 **429 `Rate Exceeded`를 그대로 받아 Job을 `FAILED`로 확정**한다 — core 30에서 18건 중 정확히 8건(= 18 − 10)이 그렇게 죽었고, 70초를 기다려도 회수되지 않았다. `ComposeJobRepository.findStalled`가 `PENDING`만 보기 때문이다.
- **후보**:
  - **동기 유지 + `core`만 키우기** — 한도가 어디 있든 넘는 순간 깨지는 성질은 그대로다. 그리고 한도를 1000으로 올리면 스레드 1000개가 8.3초씩 자고 있어야 한다.
  - **동기 유지 + 재실행이 `FAILED`도 줍기** — 영구 실패(`이미지 형식을 인식할 수 없다`, 원본 없음)와 일시 실패(스로틀링)를 가를 수단이 없다. 무한 재시도로 샌다.
  - **비동기 invoke + 앱이 S3를 확인**(결과 key `HeadObject` 폴링) — 새 인프라가 0이다. 대신 실패가 침묵이라 "아직 안 끝났다"와 "실패했다"를 영원히 구별하지 못한다.
  - **비동기 invoke + Lambda Destinations → SQS** (선택)
- **선택**: `InvocationType.EVENT`로 바꾸고, 함수에 `OnSuccess`/`OnFailure` Destination을 걸어 SQS로 결과를 받는다. `ComposeLambdaPayload`에 `jobId`를 싣는다 — Destination 통지에는 원래 요청 payload가 그대로 포함되므로 그 값으로 Job을 찾는다. 앱은 SQS 소비자를 두고 기존 `completeJob`/`failJob`을 호출한다. **`composeTaskExecutor`(스레드풀 + `LinkedBlockingQueue`)와 `@Async`는 삭제한다** — invoke가 수십 ms면 `@TransactionalEventListener(AFTER_COMMIT)`에서 직접 불러도 요청 스레드가 묶이지 않는다. **`ComposeRerunScheduler`와 `started_at` 선점은 그대로 남는다.** **`InProcessComposeExecutor`도 함께 제거하고 `LambdaComposeExecutor`를 유일한 구현으로 만든다** — 남겨두면 `ComposeExecutor.execute()`가 "다 그렸다"(in-process)와 "접수했다"(Lambda)라는 두 계약을 갖게 되어 워커가 구현을 알아야 한다. 픽셀 검증은 `compose-core`의 `FourcutRendererTest`, 다운로드·렌더·업로드 글루는 `compose-lambda`의 `ComposeHandlerTest`가 이미 덮고 있어 커버리지 손실이 없다. `compose.executor` 프로퍼티와 `ComposeConfig.fourcutRenderer()` 빈도 같이 사라진다.
- **이유**: 429는 "지금 바쁘니 나중에"라는 뜻인데 **동기 호출은 그것을 "실패"로 번역해 사용자에게 그대로 전달한다.** 비동기는 Lambda가 이벤트를 내부 큐에 쌓고 **최대 6시간 재시도**하므로 이 번역 자체가 사라진다. 위 세 문제 중 앞의 둘(스레드 점유·한도 초과 시 파손)이 없어지고, 셋째(재시도 가능/불가능 미구분)는 일시 실패를 Lambda가 삼키면서 우리 `FAILED`에 영구 실패만 남는 형태로 해소된다. **S3 확인 방식(후보 3)을 버린 이유**는 실패를 못 받으면 8/21 오전에 고친 "영원한 PENDING"이 형태만 바꿔 되살아나기 때문이다 — 그때는 큐 거부로 생겼고, 이번엔 Lambda 실패로 생긴다. **스케줄러를 남기는 이유**는 유실 지점 ①(커밋했는데 invoke 전에 서버 사망)이 이중 쓰기 문제라 SQS로도 안 닫히기 때문이다. 8/17 결정에 적은 "나머지를 치울 장치는 어차피 필요하다"가 그대로 유효하다.
- **포기한 것**: **결과 확정이 늦어진다** — 통지가 SQS를 한 번 거치므로 완료 감지가 수백 ms~수 초 밀린다(프론트가 어차피 폴링이라 체감은 작지만, 8.3초짜리 작업에 붙는 순수 추가 지연이다). **인프라가 늘었다** — SQS 큐(+DLQ)와 Destination 설정이 배포 대상에 추가된다. **오프라인에서 합성을 돌릴 수단이 없어진다** — `InProcessComposeExecutor`를 함께 지우므로, 로컬 개발도 실제 AWS(Lambda·SQS)를 거쳐야 한다(S3를 이미 그렇게 쓰고 있어 추가 부담은 크지 않지만, 네트워크가 끊기면 합성만 못 돌린다). 8/17에 적은 "그 바깥은 테스트에 안 잡힌다"가 더 넓어져 **`@SpringBootTest`는 합성 실행기를 한 번도 호출하지 않는 상태로만 돈다** — 실행기 빈은 뜨지만 가짜 함수 이름을 물고 있을 뿐이다. **`ComposeLambdaPayload`에 `jobId`가 늘어 배포 순서가 강제된다** — **Lambda 먼저, 서버 나중**이어야 한다. 순서를 지키면 무중단으로 넘어간다: Destination은 **비동기 호출에만** 붙으므로 배포 창 동안 옛 서버(동기·응답으로 직접 기록, `jobId` 불필요)와 새 서버(비동기·Destination)가 공존하고, 새 Lambda는 `jobId`가 null인 옛 payload를 그냥 무시한다(핸들러는 `jobId`를 읽지 않는다 — 원본 payload를 통지에 실어 보내는 건 AWS다). 순서를 뒤집으면 옛 Lambda가 모르는 필드를 받는다. 썸네일 도입 때와 같은 패턴이다. **한 번 깨지고 끝이 아니라, 앞으로 payload를 바꿀 때마다 같은 규칙(새 필드는 null 허용, Lambda 선배포)을 지켜야 한다** — 8/17에 적은 "배포물이 둘이다"의 구체적인 값이다. **실패를 아는 데 시간이 걸린다** — Lambda가 자체 재시도(비동기 기본 2회)를 끝낸 뒤에야 `OnFailure`가 온다. 그 사이 재실행 스케줄러가 같은 Job을 또 던질 수 있으므로 `compose.stale-after`를 **Lambda 타임아웃 × (재시도 횟수 + 1)** 이상으로 잡아야 한다(지금 값 5분은 60초 × 3 = 180초를 넘으므로 우연히 안전하지만, 근거를 명시하지 않으면 타임아웃을 올릴 때 깨진다). **호출 실패가 즉시 안 보인다** — `LambdaComposeExecutor`가 예외로 알려주던 것을 이제 DLQ/`OnFailure` 모니터링으로 알아야 한다. 실패 알림 장치가 없으면 조용히 쌓인다.
- **다시 볼 시점**: **Lambda 동시성 한도를 올린 뒤** 실제 처리량이 예상만큼 안 나오면 다음 벽(DB 커넥션 10개, 앱 CPU 2코어)을 다시 잰다 — 이번 측정은 동시성 10에 막혀 그 너머를 보지 못했다. SQS 소비자가 앱의 부담이 되거나(폴링 스레드·가시성 타임아웃 관리) 합성 외에 같은 통지 경로가 더 필요해지면 EventBridge로의 일반화를 검토. 갱신 청구의 전달 보장(기록 후보)이 "메시지 인프라를 추가하지 않는다"로 결론 나 있는데, **이 결정으로 SQS가 이미 들어오므로 그 근거가 약해진다** — 정기결제 쪽을 다시 볼 때 함께 본다.

## 기록 후보 (아직 안 씀)

- **정기결제 갱신 청구의 전달 보장 방식** — **결론은 이미 코드에 있고, 글로만 안 옮겼다.**
  후보는 RabbitMQ 영속큐+ack / 아웃박스 패턴 / DB 폴링 배치+멱등 재시도였고,
  선택은 **DB 폴링 배치**다 — `SubscriptionRenewalJobConfig`를 매일 02:00에 기동,
  일 단위 멱등키(`renewal:{subscriptionId}:{yyyyMMdd}`), PG 호출 직전 `IN_PROGRESS` 도장,
  청구 스텝에만 트랜잭션 매니저를 주지 않아 PG 호출을 트랜잭션 밖에 둔다.
  즉 결론은 "메시지 인프라를 추가하지 않는다"였다.
  **"포기한 것"에 반드시 들어가야 할 것** — 하루 1회 폴링이라 실패 복구가 최대 하루 늦고,
  **PG 호출 중 프로세스가 죽으면 `IN_PROGRESS`로 남은 주문을 아무도 회수하지 않는다**
  (다음 날 준비 스텝은 "미확정 주문 있음"으로 건너뛰기만 하고, 청구 스텝 리더는 `CREATED`만 읽는다).
  사람이 PG 콘솔을 보고 손으로 정리하기 전까지 그 사용자는 갱신이 영구히 멈춘다.
  웹훅이 붙으면 이 자리가 메워지는데, `WebhookService`는 아직 본문 길이만 로그로 찍는 스텁이다.
  **왜 그 트레이드오프를 받아들였는지는 본인이 쓰는 게 맞다.**

- **약관 동의 이력을 탈퇴 시 지울 것인가** — 이미 지우는 쪽으로 구현돼 있는데(위 약관 항목 참조)
  그 판단의 근거가 어디에도 없다. "법적 증빙"이라는 명분으로 만든 테이블을 탈퇴 때 통째로 지우는
  것이라 근거가 필요하다. 개인정보 삭제 의무와 증빙 보관 의무 중 어느 쪽을 택했는지,
  그 선택으로 무엇을 잃는지.
