# ADR-0013 · 합성 출력 무결성 — 시도 번호, 조건부 생성, 체크섬 쌍 검증, 지연 재삭제

- **상태**: 1판 — 서버·Lambda 코드(Lambda 배포·테스트 버킷 확인은 실연동 미확인)
- **날짜**: 2026-10-27
- **관련**: R5 13절(job별 고정 출력 key와 검증된 한 쌍의 성공 채택, attemptNo와 늦은 실패, 삭제·탈퇴 뒤 늦은 쓰기 정리,
  구형 payload·결과 메시지와 배포 순서), ADR-0001(합성 결과 채널)

## 0. 원칙

1. **job별 고정 출력 key 를 유지한다.** 실행별 출력 위치·출력 manifest 는 두지 않는다(R4 기본안 철회).
2. **성공은 실제 저장된 한 쌍으로 판단한다.** 단순 존재·ETag·임의 메타데이터가 아니라 S3 가 업로드 때 검증·저장한 SHA-256 이다.
3. **덮어써 복구하지 않는다.** 412 를 성공으로 바꾸지 않고, 지우고 다시 쓰지 않는다. 다른 바이트면 비공개 최종 실패(`OUTPUT_CONFLICT`).
4. **늦은 실패가 다음 시도의 성공을 버리지 않는다.** 실패 통지는 지금 시도 번호와 같을 때만 반영한다.

## 1. 출력 계약(`ComposeOutputContract`)

| 계약 | 쓰기 | 성공 응답 | 서버 확정 |
|---|---|---|---|
| 1(예전, 기본) | 무조건 PUT | `{"ok":true}` | `PENDING` 이면 완료 |
| 2(검증한 쌍) | 두 출력 모두 `If-None-Match: *` + `checksumSHA256` | 두 체크섬·시도 번호·계약 | 저장된 두 체크섬(`ChecksumMode`)이 통지와 모두 같을 때만 완료, 다르거나 없으면 `OUTPUT_CONFLICT` 최종 실패 |

- 계약은 **접수 때 작업에 고정**한다(`compose_job.render_contract`). 재시도·재실행이 계약을 바꾸지 않는다.
- 계약 2 의 Lambda 는 412 를 받으면 저장된 객체의 체크섬을 읽어 자기 바이트와 같을 때만 그 출력을 성공으로 본다(같은 입력의 재실행).
- 완료를 확정한 트랜잭션이 결과 참조·두 체크섬(`result_sha256`·`thumbnail_sha256`)·미디어·사용량을 함께 기록한다.
  이전 시도의 성공도 받는다(`PENDING` 이면) — 이미 끝난 작업을 늦은 성공으로 되살리지 않는다.

## 2. 시도 번호

- `compose_job.attempt_no` — 워커가 claim 을 이길 때마다 같은 UPDATE 에서 +1, 그 값을 payload 의 `attemptNo` 로 싣는다.
  AWS 내부 재시도는 같은 payload 라 같은 번호다.
- 실패 통지(`RetriesExhausted`)는 `attempt_no = :attemptNo` 조건부 UPDATE 로만 FAILED 가 된다. 지난 시도면 0행 → `PENDING` 그대로,
  재실행 스케줄러가 이어 간다. 번호가 없는 예전 payload 는 대조하지 않는다.

## 3. 지연 재삭제

- 최종 실패한 작업의 결과·썸네일 자리와, 합성 중 삭제 요청된 행사 작업의 결과는 **지금 한 번, `LATE_WRITE_WINDOW`(6시간 30분) 뒤 한 번 더** 지운다
  — AWS 비동기 큐 수명(최대 6시간)과 실행 시간 동안 늦게 도착한 실행이 고정 key 에 다시 쓸 수 있어서다.
- `s3_deletion.redelete_at`: 첫 삭제에 성공하면 행을 지우지 않고 다음 차례를 그 시각으로 옮긴 뒤 비운다. 재시도 배치가 그때 다시 지운다.

## 4. 배포 순서(사용자 몫 — 실연동 미확인)

1. 서버(이 변경) — 두 계약의 통지를 다 처리한다. `compose.output-contract` 는 기본 1 이라 새 작업도 예전 계약이다.
2. Lambda — 두 계약을 다 받는 핸들러. 실행 역할에 `s3:GetObject`(HeadObject + ChecksumMode)·암호화 키 권한이 있는지 테스트 버킷에서 확인.
3. `compose.output-contract=2` — 그 뒤 접수한 작업부터 계약 2. 구형 작업·DLQ 메시지는 계약 1 그대로 처리된다.
4. 반복·동시 렌더에서 결과·썸네일 바이트가 재현되는지(같은 입력 → 같은 체크섬) 공개 전 검수.
